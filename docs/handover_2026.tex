\section{起点：T-DT 开源代码的功能与不足}

\subsection{代码来源与基本定位}
上游代码为东北大学 T-DT 实验室发布的 2025 赛季雷达站开源项目（\code{T-DT\_Radar-main}，
MIT 协议，技术报告见 \url{https://bbs.robomaster.com/article/803954}）。
该项目 README 中明确说明：\textbf{"本项目提供了除串口、相机驱动、模型训练外雷达站的全部功能"}。
也就是说，感知、融合、标定与地图可视化部分是现成的，但与裁判系统的串口通信、
相机图像采集与推理模型三部分缺失，而这三部分是实际参赛不可缺少的环节。

原版硬件平台为 Livox Avia 激光雷达、海康 CH-120-10UC 相机、i7-12700KF 处理器与
RTX A4000$\times$2 显卡。本战队硬件为 Livox Mid-70 激光雷达、海康 6MP 相机，
整机为惠普暗影精灵 10 笔记本电脑（RTX 4060 显卡），并专门购置 1TB 固态硬盘用于雷达站数据存储。

\subsection{原版代码结构}
\begin{itemize}
  \item \code{src/tdt\_vision/}：相机标定（calibrate）、目标检测（detect）、坐标解算（resolve）、
        推理加速（infer）、通用工具（utils）
  \item \code{src/lidar/}：点云配准（localization，CPU GICP）、欧式聚类（cluster）、动态点提取（dynamic\_cloud）
  \item \code{src/fusion/}：卡尔曼融合跟踪（kalman\_filter）、地图可视化（debug\_map）
  \item \code{src/interface/}：自定义消息定义（DetectResult、MatchInfo、Radar2Sentry 等）
  \item \code{src/livox\_driver/}：Livox 雷达驱动（本项目直接沿用）
  \item \code{src/utils/}：rosbag 回放工具（rosbag\_player）、模型格式转换脚本（onnx2trt.py）
\end{itemize}

原版代码模块划分清晰、耦合度低，具备良好的可扩展性。但各模块实现较为基础：
detect.cpp 仅 334 行、kalman\_filter.cpp 仅 206 行、debug\_map.cpp 仅 285 行、
resolve.cpp 仅 141 行、localization.cpp 仅 187 行。
核心逻辑虽然完整，但整体只满足实验室环境下的回放验证，与实际参赛要求存在较大差距。

\section{各模块改造说明}

\subsection{相机驱动（自主开发）}
原版未提供相机驱动，仅定义了 \code{camera\_image} 话题，默认图像采集已由外部完成。
本项目接入海康 MV-CS060 的 SDK（\code{src/tdt\_vision/camera/MV\_SDK}），
编写 \code{hik.cpp} 完成图像采集、曝光控制与内参数加载，并发布至 \code{camera\_image} 话题。
夜间场次曝光参数单独保存于 \code{config/camera\_driver\_night.yaml}。

\subsection{检测模块 detect：超分、3D 框与 5 槽位输出}
原版 334 行，仅实现 YOLO 检测与装甲板分类。本项目主要改动：
\begin{enumerate}
  \item \textbf{增加 SR 超分}：先以较低分辨率完成快速检测，再对感兴趣区域做超分辨率放大。
        训练与转换脚本为 \code{utils/create\_sr\_onnx.py} 与 \code{utils/pb2onnx\_sr.py}。
  \item \textbf{增加 3D 框}：利用外参将检测框投影回三维空间，在检测窗口中叠加蓝色长方体。
  \item \textbf{增加 5 槽位输出}：按 2026 赛季规则，将装甲板数字映射至槽位
        （1 英雄、2 工程、3 步兵三号、4 步兵四号、6 哨兵；2026 赛季无步兵五号与空中单位），
        写入 \code{DetectResult} 的 \code{red\_x/blue\_x} 数组。
        该部分存在一项缺陷，详见 \S4.2（同号覆盖）。
\end{enumerate}

\subsection{融合模块 kalman\_filter：身份锁定与盲区预测}
原版 206 行，仅实现基础卡尔曼跟踪。本项目扩展至 1488 行，主要变化：
\begin{itemize}
  \item \textbf{Hungarian 匹配}：对 KF 轨迹与新检测结果做二分图最优匹配，
        避免同一目标匹配至多条轨迹。
  \item \textbf{id\_score 身份置信}：为每条轨迹维护身份置信度，仅在装甲板数字识别结果
        稳定时赋值，避免偶发误分类直接改写目标身份。
  \item \textbf{行为分类预测}：目标进入盲区后保持轨迹，依据位置与速度推断其行为类别
        （CHARGING/TUNNEL/OUTPOST/ASSEMBLY 四类）并对位置进行预测，
        目标重新可见后即可接管。
  \item \textbf{发布 \code{/radar2sentry}}：将融合后的 5 槽位坐标发送至串口节点。
\end{itemize}

\subsection{标定模块 calibrate：按 2026 场地重做五点流程}
在原版五点标定（回车开始、方向键微调）基础上扩展至 451 行：
标定点按 2026 场地更新（我方堡垒、我方前哨、敌方基地、敌方前哨、中央高塔），
外参按红蓝双方分色保存为 \code{config/\{red,blue\}/out\_matrix\_*}，
并通过检测窗口中的 3D 框直观验证标定贴合程度。
\textbf{重要经验：雷达每场比赛后如被搬动，外参即失效，局间必须重新标定}。

\subsection{解算模块 resolve：增加 HeightGrid 地形修正}
原版 141 行，仅做平面透视变换。本项目增加 HeightGrid：预先计算
\code{config/map/field\_mesh.bin} 网格高度，像素投影至世界坐标时查询实际地面高度
加以修正，扩展至 329 行。

\subsection{配准模块 localization：CPU GICP 改为 CUDA ICP}
原版 187 行使用 CPU GICP 配准，本项目改为 CUDA ICP（\code{cuda\_icp.h}），共 483 行。
场地地图 \code{config/map/map.pcd} 同步更换为 2026 赛季场地扫描点云。

\subsection{串口通信：自主开发（参赛核心环节）}
该模块为原版所没有的内容，也是 2026 赛季问题最集中的部分。
自主编写的 \code{radar\_serial\_node.cpp} 实现以下功能：
\begin{itemize}
  \item 0x0305 小地图上传：敌方与己方各 6 个坐标（48 字节），频率不超过 5Hz，
        单位为厘米，坐标置 0 表示未发送。官方标记精度规则：偏差 $<$0.8m 计 +1，
        0.8$\sim$1.6m 计 +0.5，$\ge$1.6m 计 $-$0.8。
  \item 0x0301 与 0x0121：双倍易伤决策包（每局 2 次机会，每次 30 秒）。
  \item 0x0303：下行数据解析（比赛状态与血量）。
  \item 0x0001/0003/0101/0105/020C/020E 汇总发布至 \code{/match\_info}：
        其中 0x020C 为标记成功位，0x020E 的 bit0-1 为双倍易伤机会数、bit2 为激活状态。
\end{itemize}
\textbf{串口节点本身只负责数据转发，实际发送的车辆数量完全由上游 detect 与 kalman
模块决定}。2026 赛季的主要问题即出在数据上游，详见 \S4。

\subsection{可视化模块 debug\_map：盲区预测点与双倍易伤自动触发}
原版 285 行，仅作地图显示。本项目扩展至 728 行，增加：
\begin{itemize}
  \item \textbf{盲区预测点}：目标进入盲区时，在地图上按行为分类显示预测位置。
  \item \textbf{双倍易伤自动触发}：当机会数大于已触发数、场上存在有效标记且当前未处于
        激活状态时，自动发送 \code{/radar/decision\_request}；同时保留手动方式
        （小地图窗口按 \code{v} 键）作为备份。
\end{itemize}

\subsection{工具链：控制面板、录包工具与超分训练}
原版仅提供 rosbag\_player 回放与 onnx2trt 转换脚本。本项目新增：
\begin{itemize}
  \item \code{rm\_control\_panel}（Qt 控制面板）：比赛期间切换队伍颜色、触发标定、
        开关录包，无需修改配置文件并重启。
  \item \code{databag\_tool}：专用录包工具，按场次自动命名并保存至 \code{bags/} 目录。
  \item \code{create\_sr\_onnx.py} 与 \code{pb2onnx\_sr.py}：SR 超分模型的训练与格式转换。
\end{itemize}

\section{赛场应用效果与遗留问题}

\subsection{系统运行情况}
2026 区域赛局均易伤约 475 秒/局，处于较低水平。回放验证表明，识别与定位功能本身
精度良好，\textbf{问题不在感知环节，而在发送给裁判系统的数据内容}。
使用 \code{tools/analyze\_vuln\_bag.py} 对比赛回放包解码统计，结果如下：

\subsection{双倍易伤未能触发的原因分析}
原因链条如下：
\begin{enumerate}
  \item detect 模块填写槽位时，若两辆车得到相同编号，\textbf{后写入的数据直接覆盖先写入的
        数据}，且无置信度仲裁（即 \S3.2 所述缺陷）；
  \item 车辆可见但未识别出装甲板数字时，编号置为 $-$1，该车整帧不发送；
  \item 上述两条导致每帧仅发送 1$\sim$3 辆车（对浙江大学一队一局统计，平均 2.26 辆，
        99\% 的时间不超过 3 辆）；
  \item 已发送坐标存在精度不足问题，按官方规则偏差 $\ge$1.6m 时倒扣分数；
  \item 整场比赛 0x020C 标记成功位从未出现上升沿；
  \item 0x020E 机会数始终为 0，自动触发条件永远无法满足，\textbf{双倍易伤激活时长为 0 秒}。
\end{enumerate}
\textbf{根本原因并非双倍易伤触发逻辑本身，而是发送车辆数量不足与坐标精度不足，
导致标记机制未能有效发挥作用}。

\subsection{赛事启动故障及对策}
区域赛中有一局雷达未能正常启动，双倍易伤自然全程未能触发。
原因在于 3 分钟准备时间内接线与配置未能完成，且缺少强制性的赛前自检环节。
相应对策已写入 \code{docs/preflight\_check.md}（赛前六项验证清单）。

\section{2027 赛季注意事项}

\begin{enumerate}
  \item \textbf{车型变化}：2027 赛季机器人数量减少一个。需按新赛季规则手册核对并修改：
        \code{robot\_slots.h} 槽位表、\code{radar\_serial\_node.cpp} 协议映射、
        \code{armor\_class\_to\_slot} 映射、0x0003 血量表下标。修改后必须进行全链路回放回归测试。
  \item \textbf{装甲板样式变化}：若 2027 赛季装甲板样式有变化，现有 \code{classify.onnx}
        与 \code{armor\_yolo} 模型可能无法直接适用（训练数据不包含新样式），
        应尽早收集相关数据并重新训练。
  \item \textbf{优先修复项}：一是修复槽位同号覆盖问题；二是将发送数据源改为 KF 轨迹直接输出，
        不再依赖装甲板数字识别结果；三是增加置信度门控，坐标偏差过大时置零不发送
        （协议中坐标置 0 即视为未发送）。
  \item \textbf{流程规范}：赛前必须完整执行 \code{docs/preflight\_check.md} 检查清单；
        并使用 \code{tools/analyze\_vuln\_bag.py} 对试运行回放进行统计，
        平均发送车辆数 $\ge$3.5、发送 $\ge$3 辆占比 $\ge$80\% 达标后方可上场。
\end{enumerate}
