\section{起点：拿到的 T-DT 开源是什么样的}

\subsection{来源与定位}
上游是东北大学 T-DT 实验室的 2025 赛季雷达开源（\code{T-DT\_Radar-main}，
MIT 协议，技术报告见 RM 论坛 \url{https://bbs.robomaster.com/article/803954}）。
README 里明确一句话：\textbf{"本项目提供了除串口、相机驱动、模型训练外雷达站的全部功能"}。
也就是说，感知 + 融合 + 标定 + 地图可视化是现成的，但\textbf{与裁判系统通信、取图、推理模型三块是空的}，
而这三块恰恰是上场最关键的部分。

原版硬件平台：Livox Avia + 海康 CH-120-10UC + i7-12700KF + RTX A4000$\times$2。
我们的硬件：Livox Mid-70 + 海康 6MP + i7 + RTX 3050M（算力弱很多，直接影响推理方案选择）。

\subsection{原版代码结构（我们拿到的)}
\begin{itemize}
  \item \code{src/tdt\_vision/}：相机标定(calibrate)、检测(detect)、解算(resolve)、推理(infer)、工具(utils)
  \item \code{src/lidar/}：localization(GICP 配准)、cluster(欧式聚类)、dynamic\_cloud(动态点)
  \item \code{src/fusion/}：kalman\_filter(卡尔曼融合跟踪)、debug\_map(地图可视化)
  \item \code{src/interface/}：自定义消息(DetectResult/MatchInfo/Radar2Sentry 等)
  \item \code{src/livox\_driver/}：Livox 驱动（原版自带，我们直接沿用）
  \item \code{src/utils/}：rosbag\_player 回放工具、onnx2trt 转换脚本
\end{itemize}
模块化做得很清楚，低耦合，确实易于扩展。但每块都是"骨架"：
detect.cpp 只有 334 行、kalman\_filter.cpp 206 行、debug\_map.cpp 285 行、
resolve.cpp 141 行、localization.cpp 187 行。\textbf{核心逻辑都在，但只够跑通"实验室回放"，离上场差很远}。

\section{逐模块改造记录}

\subsection{相机驱动（从无到有)}
原版没有相机驱动（README 说的"不含相机驱动"），只有 \code{camera\_image} 这个 topic 假设图已经来了。
我们接入海康 MV-CS060 的 SDK（\code{src/tdt\_vision/camera/MV\_SDK}），
写 \code{hik.cpp} 封装取图、曝光控制、内参加载，发布到 \code{camera\_image}。
夜场曝光参数单独存 \code{config/camera\_driver\_night.yaml}。

\subsection{检测 detect：加超分、加 3D 框、加 5 槽输出}
原版 334 行只做 YOLO 检测 + 装甲板分类。\textbf{我们 RTX 3050M 算力远不如原版 A4000$\times$2}，
直接跑 1280 输入太慢，所以：
\begin{enumerate}
  \item \textbf{加 SR 超分}（15 处相关代码）：先用小分辨率 YOLO 快检，再对 ROI 超分辨率放大，
        在算力弱的卡上提高小目标识别率。训练脚本 \code{utils/create\_sr\_onnx.py}、
        转换 \code{utils/pb2onnx\_sr.py}。
  \item \textbf{加 3D 框}：用外参把检测框投回 3D，在 detect 窗口叠加蓝色长方体，
        直观看出标定准不准（原版只出 2D 框）。
  \item \textbf{加 5 槽位输出}：按 2026 规则把装甲板数字映射到槽位
        （1$\to$英雄、2$\to$工程、3$\to$步兵3、4$\to$步兵4、6$\to$哨兵，2026 无步兵5 无空中），
        填到 \code{DetectResult} 的 \code{red\_x/blue\_x} 数组。
        \textbf{这里有个大坑见 \S5.1：同号覆盖}。
\end{enumerate}

\subsection{融合 kalman\_filter：从简单跟踪到身份锁定 + 盲区猜点}
原版 206 行只做基础卡尔曼跟踪。我们扩到 1488 行：
\begin{itemize}
  \item \textbf{Hungarian 匹配}：KF 轨迹与新检测做二分图匹配，避免"同一辆车配到两条轨迹"。
  \item \textbf{id\_score 身份置信}：每条轨迹维护一个"这辆车到底是谁"的置信度，
        装甲板数字稳定才赋值，避免偶发误分类直接改写身份。
  \item \textbf{行为分类猜点}：车进盲区后不丢轨迹，按位置+速度推断行为
        （CHARGING/TUNNEL/OUTPOST/ASSEMBLY 四类）猜它在哪，恢复后接管。
  \item \textbf{发布 \code{/radar2sentry}}：把融合后的 5 槽坐标发给串口节点。
\end{itemize}

\subsection{标定 calibrate：按 2026 场地重做 5 点流程}
在原版 5 点标定（Enter 开始、wasd 微调）基础上扩到 451 行：
标定点按 2026 场地更新（我方堡垒 $\to$ 前哨 $\to$ 敌方基地 $\to$ 敌方前哨 $\to$ 中央高塔），
外参按红蓝分色保存 \code{config/\{red,blue\}/out\_matrix\_*}，配合 detect 3D 框直观验证贴合度。
\textbf{关键实战教训：雷达每场被搬动过外参就失效，必须每场间重标}。

\subsection{解算 resolve：加 HeightGrid 地形修正}
原版 141 行只做平面透视变换。\textbf{RMUC 场地不是平的}（有 43 度坡、高低台），
直接平面投会偏。我们加 HeightGrid：预计算 \code{config/map/field\_mesh.bin} 网格高度，
把像素投到世界坐标时用网格查实际地面高度修正，329 行。

\subsection{配准 localization：CPU GICP $\to$ CUDA ICP}
原版 187 行用 CPU GICP 配准，我们 483 行改成 CUDA ICP（\code{cuda\_icp.h}）。
原因还是算力：CPU 配准在前几帧收敛慢，场上没法等。GPU 化后前几帧即可对齐。
地图 \code{config/map/map.pcd} 换成 2026 场地扫描点云。

\subsection{串口通信：从零自研（上场必须)}
\textbf{这是原版完全没有的部分，也是上场最关键、2026 出问题最多的部分}。
自研 \code{radar\_serial\_node.cpp}：
\begin{itemize}
  \item 0x0305 小地图上传：6 敌 + 6 己方坐标（48B），$\le$5Hz，cm 单位，x=y=0 视为未发送。
        标记精度：$<$0.8m 计 +1，0.8$\sim$1.6m 计 +0.5，$\ge$1.6m 计 $-$0.8。
  \item 0x0301 + 0x0121：双倍易伤决策包（每局 2 次，每次 30s）。
  \item 0x0303：下行解析（比赛状态、HP）。
  \item 0x0001/0003/0101/0105/020C/020E $\to$ \code{/match\_info}：
        0x020C = 标记成功位，0x020E bit0-1 = 机会数、bit2 = 激活中。
\end{itemize}
\textbf{串口节点本身只是搬运工，发几辆车完全由上游 detect/kalman 决定}。
2026 的核心问题就在这里（\S5）。

\subsection{debug\_map：加盲区猜点、双倍易伤全自动}
原版 285 行只做地图显示。我们 728 行加：
\begin{itemize}
  \item \textbf{盲区猜点}：车进盲区时在地图上按行为分类显示预测位置。
  \item \textbf{双倍易伤全自动触发}：条件 = 机会数 $>$ 已触发数 且 场上有标记 且 非激活
        $\Rightarrow$ 自动发 \code{/radar/decision\_request}。
        手动兜底：小地图窗口按 \code{v} 键。
\end{itemize}

\subsection{工具链：控制面板、录包工具、SR 训练}
原版只有 rosbag\_player 回放和 onnx2trt 转换。我们新增：
\begin{itemize}
  \item \code{rm\_control\_panel}（Qt）：比赛时改 team、触发标定、开关录包，不用改文件重启。
  \item \code{databag\_tool}：自研录包，按场次自动命名到 \code{bags/}。
  \item \code{create\_sr\_onnx.py} / \code{pb2onnx\_sr.py}：SR 超分模型训练 + 转 onnx。
\end{itemize}

\section{2026 上场效果与遗留问题}

\subsection{能跑，识别准，但易伤很差}
局均易伤约 475s/局（较差）。回放中识别和定位本身跑得很准，
\textbf{问题不出在感知，出在"往裁判系统发什么"}。用 \code{tools/analyze\_vuln\_bag.py} 解码回放包：

\subsection{为什么双倍易伤一次都没开成}
因果链：
\begin{enumerate}
  \item detect 填槽时两车若得到相同 number，\textbf{后写直接覆盖先写}（\S3.2 的 5 槽输出大坑）
  \item 看得见车但没识别出装甲板数字 $\Rightarrow$ number=-1 $\Rightarrow$ 整车不发
  \item 结果每帧只发 1$\sim$3 辆（浙大1 平均 2.26 辆，99\% 时间 $\le$3 辆）
  \item 发出去的坐标精度不足，按规则 $\ge$1.6m 倒扣分
  \item 整场 0x020C 标记成功位\textbf{从未出现上升沿}
  \item 0x020E 机会数恒为 0 $\Rightarrow$ 自动触发条件永不满足 $\Rightarrow$ \textbf{双倍易伤 0 秒}
\end{enumerate}
\textbf{根因不是双倍易伤按钮逻辑本身，而是发车少 + 精度差让标记机制空转}。

\subsection{两场未启动事故}
区域赛有一局雷达完全没能启动，双倍易伤自然全程未开。
归因：3 分钟准备时间内接线/配置未完成，且没有强制赛前自检。
对策已写入 \code{docs/preflight\_check.md}（赛前六项验证清单）。

\section{2027 赛季注意事项}

\begin{enumerate}
  \item \textbf{车型变化}：2027 赛季少一个机器人。需改：
        \code{robot\_slots.h} 槽位表、\code{radar\_serial\_node.cpp} 的协议映射、
        \code{armor\_class\_to\_slot} 映射、0x0003 HP 表下标。
  \item \textbf{重装/新型装甲板}：若 2027 装甲板样式有变化，
        现有 \code{classify.onnx} 和 \code{armor\_yolo} 很可能不能直接用，
        训练数据里没有新样式，需尽早收集重训。
  \item \textbf{优先修复}：P1 同槽覆盖 $\to$ P2 KF 轨迹直出数据源（不依赖装甲板数字才发车）
        $\to$ P3 置信门控（发偏了不发，x=y=0 视为未发送）。
  \item \textbf{流程}：赛前强制跑 preflight 清单 + 回放判据达标才上场
        （用 \code{tools/analyze\_vuln\_bag.py}，平均发车数 $\ge$3.5、$\ge$3 辆占比 $\ge$80\%）。
\end{enumerate}
